# 知识锁网络设计

版本：draft-0.5 · 2026-11-12。配套版本见[索引](index.md)。本次补齐关系规则、前置核查与绘图方式和成本确认，执行效果待继续实践检验。

帮助使用者完成本轮约定范围内的知识锁设计。方法以[工作流](workflow.md)为准，图式、填写区和检查题以[工具卡](templates/index.md)为准；本文件编排它们的使用，不另立概念或字段。所有相对路径以本文件所在目录为起点，用户产物写入用户项目，不写进工具包安装目录。

## 1. 读取当前任务，选择材料

本包采用**一个主Skill＋三个过程Skill**，在同一任务中顺序接续，无需为每一步另开对话或启动代理。主Skill负责范围、材料、结构绘图、内容检查和整体接续；[提案Skill](skills/knowledge-gate-propose/SKILL.md)负责补充意愿、具体提案与绘图前确认；[说明Skill](skills/knowledge-gate-explain/SKILL.md)负责已加入的新内容清单及亲历讲解；[排版Skill](skills/knowledge-gate-layout/SKILL.md)负责最终视觉整理。由本入口直接读取过程文件并执行，不依赖宿主自动发现子目录；不能只安装其中一个文件夹。

完整交付顺序：**整理材料 → 提案Skill确认补充范围及具体方案 → 主Skill按已确认内容绘图并检查 → 说明Skill → 排版Skill → 成果审阅与返修 → 按需开发交接**。初绘就应用基本样式，最终排版在说明完成后执行。只整理原设计或已有明确决定时沿用，不制造额外提案或重复确认；局部返修只重做受影响步骤。

首次进入任务先读[包索引](index.md)和[工作流](workflow.md)，理解概念、范围与使用过程；同一对话已读且版本未变时无需重复全文。继续既有任务时，读取任务入口、当前有效图与附注、相关输入、作者决定及待处理事项，再读取本轮需要的卡。

| 用户当前要做什么 | 阅读与使用 | 本轮主要结果 |
| --- | --- | --- |
| 从自然语言谜题或局部构想开始 | [局部知识锁设计卡](templates/local-lock.md)，涉及多个单元时再读网络卡 | 局部设计及具体补充草案，必要时连接成网络 |
| 联系已有局部、检查或修改网络 | [网络组织卡](templates/network.md)；需改局部时读局部卡 | 有依据的跨单元联系、共享引用和修订结果 |
| 把已审阅设计交给开发 | [开发交接附页](templates/handoff.md)；回查涉及的局部/网络 | 已定范围的操作、条件、变化、反馈与验收说明 |
| 理解概念或学习手工使用 | 工作流及相关卡内教学例 | 对当前问题的解释或手画指引 |

不要为了走完流程而重建已有设计或读取无关材料。跨游戏阶段的完整任务按内容联系安排小步骤；游戏阶段只是材料定位，不能替代任务的完成范围。

## 2. 明确范围、绘图选择与输出位置

从用户要求和已有任务中确定本轮问题、输入、当前有效稿、产物位置和完成范围；已有明确约定直接沿用。设计前置不明时先查材料并集中询问，不自动当作需要新设计的缺口。

**需要绘图或改图时，由用户决定绘图方式和目标软件。**

- 尚未选择时，询问本轮采用手工、AI辅助还是混合方式，以及使用哪个画板/文件。可将问题合并为一句：“这次希望你参照工具卡手画，还是由AI辅助绘制？希望用哪个画板或文件形式？”不预选平台。
- 已明确的部分直接沿用，只问缺失的部分。例如已选某画板但未给本次目标，先定位目标，不再重问软件偏好。
- 等待选择期间可读取和整理材料；选择明确前不替用户生成特定格式图稿，不因卡内含Mermaid而默认输出Mermaid。
- 用户只要求概念解释、文字检查或开发交接时，不为使用Skill额外要求选择绘图软件。

按所选方式执行：手工路径提供卡片，不强迫另存机器格式；混合路径明确谁改哪部分。AI绘图先读[绘图方式与成本选择](references/drawing-methods.md)，检查API、CLI、原生文件或代码导入及读回能力。只能依靠Computer Use、反复截图定位和拖拽时，必须先说明限制及可能增加的token/时间消耗，询问是否继续及是否需要替代建议，不能自动切换。已有明确路径与检查范围沿用；实质变化再问。三种预设仅供选择，不擅自换平台。

**图稿与逐锁说明分别确认输出位置。**需要交付说明时，一并询问尚未明确的目标与格式：当前对话、本地文件或指定在线文档；使用已有文档时明确章节与追加/替换范围。已明确选择直接沿用。任务记录路径、画板地址或旧草稿不自动代表说明目标，不能默认新建文档或写入画板所在页面。等待选择时可整理草稿，实际写入等待目标明确。具体说明格式见[逐锁说明卡](templates/walkthrough.md)。

原始策划与当前改稿分开。首次实践保存或引用可定位的起点；后续新增材料记录版本与采用决定，不覆盖起点。多份输入冲突时指出具体差异，请作者决定影响设计的取舍；只读到截图、旧图或局部内容时说明读取范围。

## 3. 按工具卡整理内容，先确认提案再绘图

使用所选卡的实际填写区或其图式，省略不适用栏目；绘图前必须读[画板样式卡](templates/board-style.md)并应用固定颜色、形状、尺寸和三角层级。兴趣点、知识（含前置知识）和反馈为大节点，线索为小节点；不能只改颜色和形状而保持等大。图上只放短标签和必要关系，长解释与审阅内容保存在图外，不另造全量节点表或专用数据格式。

1. 从材料辨认兴趣点、可接触信息、预期认识、操作、反馈及实际条件。不要把作者知道的真相提前给玩家，也不要把每个教程步骤强制变为知识锁。
2. **先查来源再连线。**按[工作流第2.2—2.3节及4.2节](workflow.md)逐条核对本轮C的K来源、用途及材料/作者决定；同一前置复用，不同内容分开，不明先问，作者也未定则标“未知前置”。不能把C换名为K以补齐入边。前置知识必须经C到I，禁止K→I/K→F；C还须直接连接所属I。多反馈合成认识时保留各输入的共同作用；访问条件不替代知识来源。
3. 调用提案Skill处理设计缺口及新增设计性推断：先依已有选择或询问明确是否需要补充，再在图外提出具体方案、取得作者决定。**含未确认提案的图稿不得先行绘制或写入画板。**确认前可以整理原文、分析关系和提出文字方案；取得决定后才形成相应图稿。纯缩写、编号或排版不算新增设计。
4. 分开写“玩家在游戏内从哪里接触信息”和“这项设计根据哪份材料或决定”。角色陈述、作者设定和玩家能验证的证据不得混为一谈。
5. 依据工作流区分认识与实际访问条件、行动与可见反馈。K→C只表达有依据的前置用途，设计者配置材料的理由放在图外附注。不能从叙述顺序直接增设程序门禁。

绘图依据原设计和提案Skill交出的已确认范围；新增内容在实际节点、连线、条件或图像标题前保留“提案＋稳定编号”，表示采纳补充的来源，不能以颜色或总声明代替。沿用N/P编号；只有连线新增时只标该连线。采纳不等于已绘制，完成图稿后再核对哪些内容实际加入。

未定、拒绝或暂缓的具体提案保留在图外记录，不混入有效图；已有设计的来源缺口可按工作流标“未知前置”，它不是被采纳的新设计。旧稿已有未确认补充时，先按提案Skill取得具体处理决定再返修，不默认为已采纳，也不擅自清空原画板。

完整整理任务要对照输入核对所有已成文内容的去向；可以按内容联系分步推进，但不能用几个示例替代整体覆盖。仅需解释或检查局部时，保持用户指定范围。

## 4. 检查、集中审阅与返修

先按工作流4.5节分别检查连接结构、前置依据和未知项，再沿整体目标与局部故事两条主线检查。关系错误返回绘图，来源不明返回材料查证/询问，需要新增设计才返回提案Skill。未知占位不计为已解决，不能只凭每条C有K入边宣布完成。无上游知识锁、回环或无独立验证行动不自动判错。

绘图前的提案确认与绘图后的成果审阅分开。前者决定加入什么，后者检查实际结果是否落实决定、表达清楚。发现新的设计补充时返回提案Skill，不能以最终审阅代替绘制前确认；没有新增的外观修改按既有范围直接进行。

提交前先执行**说明Skill**：核对输出位置，按[逐锁说明卡](templates/walkthrough.md)先列本轮“已加入的新内容”，再以带节点引用的第二人称逐锁讲解；随后执行**排版Skill**：整理主次、三角结构、单元间距、样式与布线，查看最终载体。清单只收录已确认且实际入图的新内容，未定和已采纳但未落实的项目留在记录中。

最终核对图稿与说明的版本、节点编号、名称及关系一致。排版若调整标签，返回说明Skill同步受影响文字；设计关系变化返回设计步骤。纯位置调整不重写全文。交付同时提供用户选定的图稿与说明入口。

返修时先读取用户当前图和手工修改，定位受影响的共同内容及其用途，再更新图、必要附注与已有交接中的相关引用。不能凭上一轮生成文本覆盖新稿；无法读取现行图时先取得可用的当前材料，所提修改保持建议状态。完成后读回实际产物，核对改动和受影响联系；只能检查局部时如实限定结论。

设计变化后先确认新增提案，再修改图稿、同步实际新增清单与受影响的逐锁说明，最后整理受影响布局。过程技能发现内容矛盾时返回设计步骤，需要补充时由提案Skill取得决定，不以改写故事或隐藏连线来通过检查。

优先调整局部和网络；确需改变外部阶段、故事或宏观目标时，说明具体影响并在用户范围内推进。使用者的源文和游戏工程不因调用本Skill就自动获得改写授权。

## 5. 交接与任务接续

需要进入开发时使用交接附页，引用当前已审阅设计，补足实施真正缺少的信息。可以交接已定部分，标明其余未定项的影响；不能将“玩家理解了”直接变成程序状态。代码、引擎接口和实际实现由后续开发任务读取项目后决定。

沿用用户项目已有记录。持续设计任务若没有记录，保存一份简短记录即可；一次概念问答无需建立正式任务。记录内容按[工作流第7节](workflow.md)执行，至少能追溯本轮输入与工具版本、有效产物、补充与作者决定、实质修改理由、未定影响及下一步。不要回写历史记录使其看起来当时已经知道后来的决定。

继续新对话时留下可读取的任务、当前图/附注和记录入口、实际使用版本及下一步；接手后先读取，不从聊天摘要重建平行设计。工具本身若妨碍使用，记录具体问题和改进提案；获准维护工具包时再修改并记版本，不把一份游戏实案的特例直接变成通用要求。

交付时简要说明产物在哪里、哪些补充待作者决定、实际检查了什么及下一步。分别记录设计审阅、实现进度和实际验证；格式、链接或图稿检查不能证明玩家理解或工具有效。以约定范围判断完成，不自动扩展为全游戏设计、实际开发或发布。
