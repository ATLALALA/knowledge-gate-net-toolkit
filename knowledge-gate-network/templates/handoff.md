# 开发交接附页

版本：draft-0.6 · 2026-11-24。同步K–C–I–F定义与交接教学例，保留设计和实现状态的区别。

本附页用于将已审阅的知识锁设计交给开发者或协助开发的AI。它补齐实现所需的信息，不要求每张局部卡都填写。图、线索正文及设计决定继续保留在原有材料中；本页引用这些内容，只写还需要落实的操作、条件、变化和检查情境。

## 何时使用

当[局部设计卡](local-lock.md)或[网络组织卡](network.md)已经明确某段设计，准备制作一个交互、一个信息入口或一段可体验内容时使用。可以只交接其中已确定的部分，并说明其余部分如何影响开发。

| 项目 | 内容 |
| --- | --- |
| 输入 | 当前设计图及版本、已确定的节点或关系、作者审阅决定、必要文本或图片，以及开发项目中已经确认的约束 |
| 产出 | 一段可定位到设计的实施说明、可观察的验收情境、尚未解决的影响及实现/验证状态 |
| 使用者 | 设计者、开发者或协助开发的AI；手工整理即可，不要求安装Skill或维护机器数据 |

若关键操作或反馈仍未决定，先在原设计中明确或标为待设计；不要把补出的机制默认为原设计已经确认。开发项目的实际能力、入口和限制，需要接手者读取项目后核对，不在本页预设接口、脚本名称或运行架构。

## 怎样填写

1. **圈定本次交接。**引用具体图稿、版本及节点/关系，简述本次要做的内容和完成范围。编号沿用原图，图上已有的正文不重复抄写。
2. **补足实施差异。**从下表选择当前确实需要说明的项目。图里已有且足够明确的内容直接引用；不适用项可以省略。
3. **写成可观察的检查情境。**说明进入什么情境、玩家做什么、应该看到什么。涉及拒绝操作、重复触发或中断时才补相应情境。
4. **分别记录三种状态。**设计决定、实现进度和实际验证分别写明。完成了设计审阅，不表示已经实现；实现完成，也不表示玩家已经理解。

## 补充内容说明

| 内容 | 需要明确什么 | 何时展开 |
| --- | --- | --- |
| 信息与交互入口 | 玩家在哪里接触哪项信息或操作；对应哪个场景、对象或现有界面；具体文本/图像在何处维护 | 需要放置信息或建立交互时 |
| 实际条件 | 什么功能、资源、事件或物理位置使对象能接触、操作能发生；条件不足时已设计的表现是什么 | 设计存在这些条件时 |
| 玩家操作 | 玩家采取的动作、对象及关键时机；按下、持续、释放或提交等差异是否影响结果 | 需要交互或操作结果与时机有关时 |
| 系统变化 | 行动引起的对象、界面、资源、可访问区域或事件变化；变化持续多久，何时结束 | 行动确实改变系统状态时 |
| 可见反馈 | 玩家能看到、听到或读到什么，反馈在何处、何时呈现；引用原图的反馈节点 | 需要落实反馈呈现时 |
| 后续接续 | 当前结果如何影响其他已经确定的内容；继续引用共同节点或关系 | 本次修改影响其他单元时 |
| 生命周期 | 离开、返回、重试或重新进入时需要保留/恢复什么 | 这些行为会改变已确定设计时；不默认要求所有内容持久保存 |
| 验收情境 | 操作前提、玩家动作、可观察结果；涉及的文本、图像或状态变化是否与原设计一致 | 每段实际交接至少能说清如何检查其结果 |
| 未定影响 | 还缺什么决定，影响哪一项实施或验收；哪些部分已经能做，哪些部分需等待决定 | 仍有未定内容时 |

### 认识与系统条件分别处理

“玩家知道某个方法”“玩家可能由反馈理解某项规律”是设计对认识的描述，不直接转换成“已理解”的程序变量或门禁。若设计要求玩家输入答案、选择说法或完成某个操作，系统可以检查该项实际输入或动作；它只能表明相应行为发生，不能证明玩家内在理解。

例如，一次操作能使挡板升起，系统需要记录或呈现挡板的位置。设计者希望玩家由此理解某项规律，则应在设计图中说明信息依据，并在后续体验中观察；不需要仅为记录这一预期而增加“理解挡板规则”的系统状态。

### 避免两份内容同时变化

图与设计材料是本次交接的内容依据。实现中若发现操作、条件或反馈需要变化，将提案标明并回到相应节点或关系更新；交接附页改为引用新版本，任务记录保存修改理由。不要让附页中的新机制与原图的旧描述同时被当作有效设计。

## 可复制的填写区

仅复制下列区域到自己的项目记录。方括号是填写提示，可直接替换或删除；它们不是要求新增系统或逐项填满的规则。

```markdown
## 本次开发交接：[一句话描述]

设计依据：[图/材料位置与版本；相关节点或关系]
本次范围：[要交付的内容；必要时注明暂不覆盖部分]
状态：设计决定[已审阅/仍有待定]；实现[实际进度]；验证[实际做过什么或尚未验证]

### 需要落实的内容

- 信息或交互入口：[位置与原内容引用]
- 玩家操作：[动作、对象与影响结果的时机]
- 实际条件：[存在时填写；与预期认识分开]
- 系统变化与可见反馈：[变化、持续/结束条件及反馈引用]
- 接续或保留要求：[确实涉及其他内容、离开返回或重复操作时填写]

### 验收情境

| 情境与前提 | 玩家动作 | 应能观察到的结果 |
| --- | --- | --- |
| [具体情境] | [动作] | [可见结果及设计引用] |

未定项及影响：[缺失决定、影响的实施/验收范围；没有则省略]
```

若一条简短记录已足以交接，不必保留全部小标题或表格。多项交互共享一份文字或图片时，引用同一来源，不为每项交互复制一份正文。

## 教学示例：查看旧水站的值班表

以下为独立虚构的图法教学片段，用来演示如何补充交接内容。示例中的“设计已定”仅表示本例的设定；没有实际游戏实现或玩家测试。

### 示例设计摘录

这是教学示例唯一的设计内容来源，编号用于下文引用：

| 图中内容 | 设定 |
| --- | --- |
| I1 兴趣点 | 查看玻璃观察窗后的值班表，弄清当晚谁负责水站 |
| C1 线索 | 窗旁操作牌写着：“按住蓝色按钮升起挡板，松开后落下。” |
| K0 前置知识 | 委托已告知“观察窗旁操作牌说明如何查看值班表”，引导取得C1；这是本虚构例明确提供的前置 |
| K0→C1与C1→I1 | 按委托查阅操作牌；牌上方法支持查看值班表，不要求系统强制先读牌 |
| I1→F1 行动关系 | 玩家按住蓝钮查看窗口；这一操作依据C1提供的方法 |
| F1 可见反馈 | 挡板完全升起，露出值班表；当晚值班一栏写着“周岚”。松开蓝钮后，挡板重新遮住表格 |
| F1的图外认识附注 | 当晚条目支持“周岚被安排负责当晚值班”，不证明其实际到场；本片段没有定义后锁C，故不单列输出K |

### 本次开发交接：观察窗的按住查看交互

**设计依据：**上述教学设计摘录，示例版本2；实施范围为C1、I1→F1及F1的呈现。K0为已有委托内容；反馈的认识作用保留在附注。

**状态：**设计已定（本例设定）；实现未开始；未进行实际验证。

**需要落实的内容：**

- **入口：**C1显示在观察窗旁；玩家位于窗前的交互位置时可以操作蓝钮。操作牌文字及值班表条目以本例设计摘录为来源。
- **操作：**交互区分开始按住、持续按住和释放。具体键位或触屏手势由所用游戏的现有输入方式承载，不在交接中编造接口。
- **实际条件：**本片段的设备始终有电，无需额外获得权限或先阅读C1。进入窗前交互位置即可按住蓝钮；阅读操作牌不是系统开放交互的条件。
- **系统变化：**开始按住后挡板升起，升起过程中表格尚未完整露出；升起完成后保持打开，直至玩家释放操作。释放时挡板下降，最终完全遮住表格。本片段不保存挡板打开状态，离开交互位置也结束按住操作并使其下降。
- **反馈：**F1的值班表在挡板打开时可直接阅读。释放后的遮挡来自挡板位置变化，而非删除表格内容。不出现“已理解值班信息”的完成提示。
- **接续：**本交接止于观察窗与表格呈现。若后续单元需要运用值班安排这一认识，先明确其支持的C，再作为后锁前置K引用；仅当F1是形成该K的必要依据时连接F1→K。

**验收情境：**

| 情境与前提 | 玩家动作 | 应能观察到的结果 |
| --- | --- | --- |
| 玩家未阅读C1，已在窗前交互位置 | 按住蓝钮直到挡板升起完成 | 仍能打开挡板；表格完整露出，当晚条目可读为“周岚” |
| 挡板已打开，玩家仍持续操作 | 继续按住 | 窗口保持无遮挡；表格内容保持可读 |
| 挡板已打开 | 释放操作 | 挡板下降并重新遮住表格 |
| 挡板已打开 | 离开交互位置，待挡板下降结束后再返回 | 离开时结束操作；返回后挡板处于关闭状态，可再次按住打开 |

**待验证而非新增设定：**实现后检查窗前视角是否能在持续操作时读清表格。这是实际呈现与操作的验证问题；在没有实测前，不能只凭本页声明玩家能读清或能正确推断。

本例通过未读牌仍能操作的情境，区分“知道操作方法”与“系统允许操作”；通过“被安排值班”而非“确实在场”的措辞，限制反馈所支持的认识。验收只检查已设计的可见行为，玩家实际理解仍需相应体验材料。

## 交接前的简短检查

- 是否引用当前图外“已加入的新内容”、逐锁说明及提案决定记录？未采纳或已采纳但未落实的部分须说明影响，不能混成当前图中的已定实施内容。交接中需要新增设计时先提案确认，再同步原图和说明。

- 能否找到正在使用的图稿、版本及相关内容，而不凭开发者猜测？
- 操作、真实条件、系统变化和可见反馈是否足够明确？存在未定时，影响范围是否写清？
- 是否将“需要知道的方法”误写成系统必须检测到的理解状态？
- 修改是否同时影响其他使用同一知识、线索或反馈的内容？引用是否仍指向同一版本？
- 设计审阅、实现进度和实际验证是否分别如实记录？
